# Visit2Value architecture

## One workflow, business-scoped data

The default `harbour-house` workspace is a fictional hotel with Central and Garden properties. The existing `nusa-table` restaurant and small `luma-salon` example use the same tables and routes. `GET /api/state?businessId=...` selects only that business's branches, reviews, analysis runs, observations, themes, memberships, employees, tasks, handoffs, replies, and activity. `POST /api/action` requires a selected `businessId` and validates each referenced entity against it. A review's property must belong to its business. The UI business selector changes the scoped workspace; all identities and roles are synthetic.

## Review to evidence

1. Intake validates the synthetic flag, business/property, source review ID, rating, time, and original text. The review is saved as `pending` with its unmodified source wording before AI starts. `(business_id, source, source_review_id)` is unique. Identical feed replays return the existing review; changed text, rating, or property under the same key triggers a visible conflict and preserves the original evidence.
2. In live mode Jev screens for **any** specific praise, complaint, or suggestion. If Jev fails or is uncertain, OpenAI screens with the same rule. In fixture mode, exact labelled text has deterministic screening and observation results; unknown text stays searchable as `needs_review`. Generic opinions remain in the review table with no operational issue card. Each analysis run records provider, model, mode, prompt version, and safe error information.
3. OpenAI or the fixture extracts every distinct point as an observation. Each observation keeps an exact substring quote, source-language wording, normalized description, kind, sentiment, and category. `verifyEvidence` refuses invented or paraphrased quotes. A live provider error marks the review failed and retryable rather than discarding it.
4. Each observation is independently matched to an issue suggestion within its business, property, and feedback kind. Live unmatched observations create new suggested themes, so the theme catalog is an initial example rather than a fixed vocabulary. Owners may remove or reassign memberships. Support counts are distinct **source reviews**, not guests or observation rows. The original review stays one click away.
5. Priority considers owner-editable severity, distinct review count, recent review count, and possible recurrence. A single serious safety or pest report can rank high. The reason is displayed as a triage suggestion, not a factual diagnosis. A vague insect sighting is not labelled as bedbugs.

## Task and response controls

An owner proposes a task from an operational theme, edits its title and description, selects a fictional employee at the same property, and sets a due date. Approval stores a snapshot and sends it to the `WorkflowHandoffAdapter`. The current adapter only writes a `simulated_queued` handoff locally. Its payload contains business, property, assignee, due date, approved work, and review/quote references. Visit2Value remains the task source of truth.

An assigned employee can start work and submit a report. The task then waits in `reported`. The owner enters a separate verification note and only then moves the task to `resolved`. A staff demo role cannot verify; the owner may report and verify for a very small business, with both role actions recorded. This role switch is a demonstration, not secure authentication. A later related review after verification changes the theme to `recurrence` and permits a new task linked to the prior one; previous task, handoff, and resolution rows remain.

A verified resolution permits a reply draft for a linked source review. `replies.review_id` stays unique: one public reply record per review even if it supports several themes. The drafting adapter receives the **whole review**, the verified note, the business name, and summaries of other unresolved complaints. Those complaints produce a stored partial-reply warning. The owner edits and explicitly approves each warning-bearing reply. Batch approval is limited to up to ten visible drafts without unresolved concerns or high severity. Approval status is `approved_ready`; only a separate **Simulate publishing** action changes it to `simulated_published` and records local time and activity. No platform request is made. Published demo replies are historical records and cannot be edited.

## Persistence and provenance

`businesses → branches → reviews` holds original evidence. `analysis_runs → observations` holds one-to-many extracted points. `theme_memberships` connects independently extracted points to themes; one review can support several issues but counts once within each theme. `tasks → handoffs` tracks approved work and its simulated integration payload. `replies` links one source review to one verified task. `activity_events` is business-scoped and append-only for consequential actions.

`migrations/0001_initial.sql` is the original schema. `0002_hotel_workflow.sql` adds employees, report/verification/recurrence fields, reply publication metadata, and business-scoped activity without resetting existing tables. Migration and seed scripts are repeatable. The seed skips existing reviews and analysis runs to preserve source wording and owner corrections. The hotel generator is deterministic and uses no external content. Historical hotel analyses are labelled `fixture`; a new fixture review can be entered under a new database ID by exact text match. Live mode never silently substitutes fixture output for an AI call.

The source JSON files are in `data/fixtures/visit2value`; the separate hotel demo record is not seeded. Business-specific categories help presentation, while extraction can introduce new topics. The interface components and CSS are organized separately from domain and provider code so visual changes do not alter operations.
